# Performance: measurements of 8 October 2026 (branch `v2-fable`)

*[Technical index](../README.md) · [summary of 4 October](SYNTHESE.md) · [V2-fable § 6](../V2_FABLE.md)*

Measured **in the user's Chrome** (Claude extension installed, visible tab, Aqua design, launcher server on port 8000,
folder `E:\DEFA-fable`) and in Claude Code's built-in browser. It drove three fixes (lots 1 to 3 below); the "before"
and "after" figures were taken in the same browser, on the same machine.

## 1. Measurement conditions

- **Visible tab only.** In a background tab Chrome suspends rendering and delays timers: the "blocked.ms" counters of
  `tools/perf_probe.js` and the frames per second are meaningless there. Every timing below was taken with the tab in
  the foreground.
- Counters (requests, DOM elements, JSON parses) are exact; timings vary from one run to the next (same caveat as in
  the [summary of 4 October](SYNTHESE.md)) and are to be read as orders of magnitude.
- The launcher's `Sec-Fetch-Site` guard refuses navigations started by the extension (the "SOG" page shows instead).
  Measurements therefore go through `location.href` from a page already served by the launcher.

## 2. Overall picture

| Measure | Result |
|---|---|
| Script loading (My missions, Mission report, Profile) | 150 to 370 ms |
| Long tasks (> 50 ms) on these pages | none |
| After-the-fact translation (`content_i18n.js`) | 6 to 28 ms per page |
| Observers (`MutationObserver`) | < 1 ms |

Ordinary pages are therefore healthy. The outliers are two pages: the **Schedule** (many requests and JSON parses, a
large DOM) and the **Flight maps** (DOM inflated by the completion lists, heavy SIA database).

## 3. Schedule (`apps/cpco/odv_orders.html`)

| | before | after lot (1) |
|---|---:|---:|
| requests on opening | 206 | 19 |
| of which 404 responses | 48 | 4 |
| `JSON.parse` | 1,902 | 157 |
| DOM elements | ≈ 7,700 | ≈ 7,700 (unchanged) |

- **404**: an availability file was requested per pilot **and** per week, whether the pilot had declared anything or
  not. `SuiteDispos.readPilot` now filters the requested weeks through `data/disponibilites/_index.json`.
- **`JSON.parse`**: `va()` in `repository_nav.js` re-read the airline settings (`suiteVA:v1`, `suiteSources:v1`) and
  the enabled tools at **every text translated** by `K.brand` (≈ 1,900 parses per opening). They are now read through
  a memoised parse (`jsonCached`): the text is parsed again only when it has changed.
- **Remaining**: 7,700 DOM elements. Not addressed.

## 4. Flight maps (`apps/planner/map_planner.html`), Aqua design

### Before

- **15,073 elements** in the DOM, of which **13,552 `<option>`**: the `<datalist>` of zones, aerodromes and beacons
  were built at load time from the SIA database.
- First paint at **236 ms**, then three long tasks of **600 + 655 + 264 ms**: the page is frozen for ≈ 1.5 s.

### Attribution (load profile)

| Function | Duration |
|---|---:|
| `SiaBase.get()` (IndexedDB deserialisation) | 212 ms |
| `applyBase` | 140 ms |
| `renderZonePick` | 99 ms |

The database holds 7,185 airspaces, **70,962 cities** (GeoNames) and 652 MORA cells: IndexedDB's structured
deserialisation is proportional to that volume, and the cities are the largest share.

### Lot (2): completion on demand

The `<datalist>` are no longer written at load time but when their field receives focus (once per render afterwards);
zone completion is computed at focus. **15,073 → 1,555 elements**; long tasks after the first paint
**600 + 655 + 264 ms → 268 + 294 ms** (from 1.5 s to 0.55 s).

### Lot (3): cities set apart

Cities are stored under their own key of the browser database (`SiaBase.cities()`, silent migration of an existing
database). The Studio and the Flight maps read them at idle time after the first display, and before a generation
that needs them; refuelling tracks are parsed at idle time.

| | after (2) | after (3) |
|---|---:|---:|
| `SiaBase.get()` | 212 ms | 116 ms |
| `applyBase` | 140 ms | 84 to 94 ms |
| reading the cities | inside `get()` | ≈ 200 ms **off the critical path** |
| long tasks at load | 268 + 294 ms | 200 + 211 ms |

## 5. Remaining lead, reported to the BUGS SOG session (foundation)

`shared/browser_store.js`, `snapshot()` parses **every** `localStorage` key on every page (41 `JSON.parse`, 409 KB).
Shared foundation: not touched here, to be handled by the session in charge of it.

## 6. Leads not pursued

- `renderZonePick`: still ≈ 100 ms per render (`selectedAirspaces` walks 7,000 airspaces at every render).
- Airspace geometry as **compact arrays** (flat coordinates) to speed up the database deserialisation further
  (`SiaBase.get()` stays at ≈ 116 ms).
- Schedule DOM (7,700 elements).

## Addendum: lot (4)

Studio and Flight maps: the "Selected zones" summary (a filter over 7,000 airspaces and up to 400 lines written) is
recomputed only when the profile or the database has changed: 123 ms → 0 on every other render of the profile
(measured in the user's Chrome, visible tab). Commit "performance (4)".
