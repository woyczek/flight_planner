## 0. In short

- **Today** the data are regenerated by five unrelated chains: the V2 page *Settings › Maintenance* (SIA base, MORA,
  AAR tracks, other countries, aircraft types, VFR import), command lines in `tools/` (eAIP and FAA procedures, VAC
  extraction, GeoNames towns), the launcher's background thread (aircraft types), GitHub Actions (world weather) and
  by-hand git (the procedures' push). 17 sources, of which **7 have a step with no tool at all** (§ 1.3, § 1.4).
- **The screen**: one screen `#data` behind Administration (Full level), one row per source, four buttons per row
  (fetch · compile · push · clean) and the same four at the top for everything. The page chains the steps, shows the
  progress and keeps a journal; nothing to type, no file to place. Buttons are greyed with their reason when the
  launcher is missing.
- **Three decisions** (§ 2): (1) a frame screen drawn by aerodb, calling the launcher through a new `ctx.launcher`
  adapter of the frame and one job runner in the launcher, never a `fetch` in a module; (2) a row model whose states
  compare *fetched / compiled / published* with the AIRAC cycle in force and the parser version, reusing V2's age
  rules; (3) the base's compile leaves `shared/sia_base.js` (tied to the page, to IndexedDB and to Chromium's folder
  handles) for pure builders that run in a worker and write through the launcher — the same builders the dedicated
  application reuses; the Python builders (pypdf, big files) stay jobs of the launcher.
- **The open question of § 10.18** (what runs without the launcher) is answered in § 3: the parsing can; the fetching
  mostly cannot from a web page (the sources send no CORS header — verified for two of them), the publishing can
  (GitHub API, device token); only a native shell lifts the fetching limit. That is the bridge to the dedicated
  application.
- **Plan**: nine lots (§ 4), each with its tests (zone K of aerodb, zone A of the frame) and what leaves V2.

## 1. Inventory of the sources and of their chains today

### 1.1 The chain of the base, as V2 does it

1. **Fetch**: by hand. The SIA sells its XML export for 0 € per AIRAC cycle: account, "Add to cart", "Place order",
   licence accepted, download of `export_xml_bd_SIA_<date>[-vNN].zip` (5.6 MB for 10/26, read on the SIA product page
   on 26 Oct; contains `XML_SIA_<date>.xml` 27 MB and `AIXM4.5_all_FR_OM_<date>.xml` 44 MB,
   `SIA_XML_INTEGRATION.md` § 1). The page offers "Fetch the downloaded ZIP": the launcher takes the newest
   `export_xml_bd_SIA_*.zip` of the Downloads folder (`GET /__setup/sia-zip`, `tools/launch.py` `sia_zip()`), or the user
   picks the file.
2. **Extract**: the page reads the ZIP with `ZipStore.read` (`shared/zip_store.js`: the whole archive in memory, entries
   inflated by `DecompressionStream`) and writes the recognised XML into `data/sia/` through a folder handle
   (`showDirectoryPicker`: Chrome or Edge on a computer).
3. **Other countries**: buttons call `POST /__setup/aero-fetch { provider, args }`; the launcher downloads into
   `data/sia/openaip/`, `geojson/`, `aixm5/`, `zones/<zone>/` (`tools/aero_fetch.py`).
4. **Compile**: `SiaBase.rebuild` (`shared/sia_base.js`) reads the folder, parses (a `DOMParser` on the 44 MB AIXM text,
   regular-expression and DOM readers in `shared/carto/aero_symbols.js`, `shared/aero_sources.js`), applies the SIA
   priority rule, builds the zones that are active, and stores the whole base in IndexedDB (`sia-map-parser`).
5. **Publish**: the same page writes `data/sia/base/<zone>/<cycle>/<kind>.json`, `cities_major.json` and `index.json`
   (the manifest) through the folder handle of `data/` (`pubDir`, `publishSplit`); a file is rewritten only when its
   content changes; the older cycles of each published zone are removed on the way. No V2 page publishes through the
   GitHub API (`shared/sia_base.js` uses `GitHubData` to *read* only; checked 26 Oct).
6. **Push**: the "Synchronise" button: `POST /__setup/sync` → `tools/data_sync.py` commits the pool (`POOL` contains
   `sia/base`, not `proc`, `sia/vfr` nor `AircraftDB`), merges, pushes. A commit needs a trigram.
7. **Phones** read the files through the data layer (`frame/aerodb`).
8. **Clean**: "Archive the old cycles" moves the previous XML to `data/sia/_archives/<cycle>/`; "Purge" empties
   IndexedDB; the publication removes the old cycles of a zone. Nothing else cleans anything.

V2 already chains a lot ("Activate" on the zone map: downloads, last ZIPs, **one** rebuild, MORA of the new countries;
"Fetch everything and recompute"; "Purge the zone"; the list "Actions to do" for what stays manual;
`docs/MANUEL_ADMINISTRATEUR.md`, "Aeronautical data: zones of the world, sources and AIRAC cycles"). The Data screen keeps
that model; it does not start from zero.

- **G1** The procedures (rows 14, 15) are the only published data with **no push tool**: a clone of the data repository,

- **G2** The NAT tracks change twice a day but ride the base: a fresh message means a full rebuild and push. The FAA

- **G3** The SIA ZIP can never be fully automated: the licence acceptance and the account are part of the order. The

## 2. The screen

### 2.1 Rules

Those of the suite (`CLAUDE.md`): the page chains and shows progress, never a console or a file to place; four
languages; phone first and screens; floating notifications for results (`ctx.notify`); no native dialog (`ctx.ask`); the
value at the source (the row's state is computed, not patched after the fact). Added here:

1. **A button is never missing, it is grey with its reason** (§ 2.10); the screen opens on any device, and on a phone
   or a site without launcher it is a read-only dashboard of what is *published*.
2. **One job at a time** on the workstation (like V2's `AERO_LOCK`, `AIRCRAFT_LOCK`, `SYNC_LOCK`), a visible "Stop".
3. **Idempotent**: fetching what is current downloads nothing (`If-Modified-Since`, cycle in the name), compiling
   unchanged inputs rewrites nothing, pushing an unchanged tree makes no commit — as V2 does.
4. **A failure of a source never stops the others** in "All"; the summary names it.
5. **Nothing is guessed**: a row that cannot be read stays in `warnings`; a source with no tool says *what the user
   must do*, with the link and one gesture (open the page, pick the file), never a command.
6. **Licences**: ICAO and EUROCONTROL data never reach the public site; the screen publishes only to the private data
   repository; a source whose licence forbids it (DFS, `AIP_OPEN_DATA_INVENTORY.md`) has no row.

### 2.2 Who owns what, and where it lives

- **settings** owns the *Administration card* and its new button: one entry in `SogAdminLinks`
  (`frame/settings/admin_links.js`, `href: '#data'`, `where: 'app'`, `primary: true`, four-language title and sentence),
  Full level only like the others; the card test A12 counts its buttons and is updated with lot D1.
- **aerodb** owns the screen and the builders: `frame/aerodb/regen.js` (screen, states, runner contract, texts in four
  languages — a second exception, after the `.lnmperf` card, to "no interface text in aerodb": SPEC § 6 invariants 1 and

  command*), `frame/aerodb/regen_launcher.js` (the launcher runner), later `frame/aerodb/build/` (pure builders, § 4).
  Loaded on demand like `lnmperf.js`, only when the screen opens.
- **the frame** owns the address `#data` (the list `SCREENS` of `frame/app.js`, as `#roadmap` and `#conflicts`) and the
  new `ctx.launcher` (§ 2.8). **To confirm with the ergonomics session**: a frame screen rather than a module, because a
  module is a verb of the rail (seven at most) and this is an administrator's tool; the precedent is `#roadmap`
  reached from the same card.

### 2.3 The rows and their states

Layout, phone first (a card per row, stacked) and screen (a table): a header with the **cycle in force** (label,
dates, and "next cycle in n days"), the launcher state and the repository state ("data/ is a git repository with a
remote", "n commits to send"); the **"All" row** with the four buttons; then the groups:

1. **Aeronautical base, by zone** (the zones of § 2.12, France first): the zone header carries *compile* and *push* for
   the zone (a zone's files are built from all its sources together); its source rows carry *fetch* and *clean*. Sources
   of a zone: SIA, DIRCAM, openAIP, ENAIRE, FAA, NATS, UK Mil, NAV CANADA, X-Plane, MORA, NAT.
2. **Procedures**: eAIP France, FAA CIFP.
3. **VFR reporting points (VAC)**.
4. **Aircraft types and performance**.
5. **World weather** — status only (cycle of the last run read from `weather/world/index.json`), no button: Actions
   own it.

Each row shows, in order, its name, a coloured **state** word with its date, and the four 44 px buttons (icon and label
on a phone). Under a tap, a folded detail: files and sizes, the dates, the counts, the last log lines.

**State fields**, computed and never typed: `cycle` of the thing (AIRAC date or edition), `fetched` { at, bytes, files },
`compiled` { at, parserVersion, inputs (fingerprint of the files read), counts }, `published` { cycle, at,
parserVersion }, `unpushed` (committed or compiled, not on the remote). *Published* is read through aerodb's reader
(the manifest `sia/base/index.json`, a zone's `meta.json`, `proc/<cycle>/index.json`, `sia/vfr/index.json`, the
`AircraftDB/` listing); the rest comes from `GET /__setup/regen/state` (§ 2.7).

**Stale**, the pill words (priority order, one shown, the others in the detail): *newer cycle* (the cycle in force or
the next one announced is later than the thing's), *parser* (published `parserVersion` below the builders' current
version — G5), *age* (V2's rules, `aeroAge` in `shared/maintenance_page.js`: AIRAC sources against the cycle in force,
X-Plane against its label, NAT after 12 hours, anything else after 28 days), *source newer* (fetched after the last
compile, or the inputs fingerprint changed), *not pushed*. No stale reason: *up to date*.

**User, 26 Oct ("Ce fichier arrive chez l'utilisateur dans « download » (poste et/ou téléphone) pour l'import")**: a
hand-downloaded file (SIA zip, CIFP zip, NATS zip) is **picked up from the Downloads folder in one gesture**: on the
workstation the launcher lists it (`GET /__setup/downloads?glob=…`, the NATS pick-up route) and takes the newest cycle;
on a phone the file picker (`accept=".zip"`, the help says "Fichiers › Téléchargements": iOS opens no given folder); the
expected name (`export_xml_bd_sia_<date>-v<nn>.zip`, `CIFP_<yymmdd>.zip`) is checked and the cycle read from it.

### 2.4 The four verbs and "All"

| Verb | What it does | Result shown |
|---|---|---|
| **Fetch** | brings the source into the workstation's cache: a download by the launcher, or the pick-up of a file the user obtained (Downloads folder, or a file picker); for a source that needs the user (row 1, 4, 10, 13, 15 until D3), the row says *waiting for you* with one link and one gesture | files, bytes, date, "unchanged" |
| **Compile** | runs the builder on the cache: JavaScript builders for the base, Python jobs for procedures, VFR and aircraft; writes the outputs into `data/` (never a partial output: temporary file then replace) | counts, warnings (rows not read), duration |
| **Push** | commits the outputs under the author's trigram and sends them to the data repository (plan first for what is new or removed, agreement through `ctx.ask`) | commit, files changed, "nothing to send" |
| **Clean** | removes what is superseded: plan first (names and sizes), one question, then the removal | files and MB freed |

- **"All"** runs, for every row that can: fetch → compile → push, in the order of § 2.6, then offers one grouped *clean*
  with its plan. It is V2's "Activate" and "Fetch everything and recompute", with the push added. A row waiting for the
  user is skipped and listed at the end ("3 sources wait for you").
- A row can also be asked to do the steps up to a verb ("compile" runs fetch first when the cache is stale): V2's
  idempotence makes it cheap.
- **What "clean" means per source**: base — XML of earlier cycles to `_archives/`, base files of earlier cycles
  (automatic at publication, kept), countries no longer in the zones; `proc` — cycles older than the one in force and
  the next; VFR — the importer's removals (kept) and `report-vfr` `cache/` and `history/` older than N; eAIP — the PDF
  cache of earlier cycles; aircraft — stray files of `AircraftDB/` (kept) and the HTTP caches; the *device's* reference
  cache (`offline.release`) is not this screen's: it stays in Settings › Offline data.

### 2.6 Order and dependencies

### 2.8 How the screen calls it: `ctx.launcher`

A module may not `fetch` (`frame/INTEGRATION.md` § 7). Today `frame/settings/settings.js` (`setup()`) and
`frame/aerodb/lnmperf.js` (`call()`) call `__setup/…` directly: they are the frame's own and a known exception, not a
model. The Data screen asks the frame for an adapter (`frame/INTEGRATION.md` § 1: the module's agent asks, the frame
agent extends the adapter and the guide in the same commit):

- `ctx.launcher.available()` / `.info()` — the detection already done by `FrameData.launcher.detect()` (a launcher
  serves only http, so a site or an app never asks): `{ host, data, dataGit, lan }` or null;
- `ctx.launcher.call(route, body)` — JSON in and out, the header added, `{ ok: false, offline | status | message }`
  instead of an exception, a refusal reason that names the route;
- `ctx.launcher.read(dataPath, { signal, onBytes })` — a same-origin read of `data/<path>` as a stream;
- `ctx.launcher.job(route, body, { onProgress, signal })` — start, poll once a second, cancel on `signal`, resolve with
  the result; the frame keeps the polling alive while the screen is open and stops it at unmount.

aerodb receives it with `AeroDB.create({ launcher })` and gives it to the screen; the lnmperf card and the settings
`setup()` can move onto it in a later, separate lot.

**The runner contract** (what the screen needs from whoever does the work; the launcher runner is lot D2, the dedicated
application's device runner is [V3_APP_DONNEES.md](V3_APP_DONNEES.md)): `state()` → the fields of § 2.3 for every row;
`can(source, verb)` → `{ ok, reason }` (the reason is a key of § 2.10); `run(source, verb, args, { onProgress, signal })`
→ `{ ok, files, bytes, unchanged, warnings, errors }`. The screen never knows which runner it has.

### 2.9 Progress, journal, errors

- A running row shows a bar (determinate when the job gives `total`), the step label and the elapsed time, and a "Stop"
  button; the other rows' buttons are greyed with "another operation is running".
- **Notifications** (`ctx.notify`): one at the end of each verb (ok, warn with the count of warnings, err with the
  message), one at the end of "All" with the counts and the sources that failed or wait for the user; none at the start.
- **Journal**: a panel at the foot of the screen with the last 50 operations (time, row, verb, duration, result), each
  unfolding to its log; "Copy" like the diagnostics. Kept on the device, `cache/aerodb/regen-journal.json` (policy
  `cache`, never synchronised, not in a backup); the launcher also keeps the last jobs in memory so a reloaded page
  finds the running job again.
- **Errors** say what to do, not what failed: *the SIA site did not answer — try again later*, *this file is not a SIA
  export*, *the disk is full (needs about 200 MB)*; the technical text is in the journal.

### 2.13 Security

The routes are the workstation's (§ 2.7); a fixed list of sources and verbs; arguments validated; subprocesses are
launched with `sys.executable`, a fixed script list and `-I`-style isolation for anything that reads a downloaded file
(`CLAUDE.md`, untrusted data); downloads only from the declared hosts (the CSP list `tools/csp_policy.py`, the sites
setting); written paths stay under the four roots; no token is read or shown; the GitHub token never reaches the
launcher (push is git with the workstation's own credentials). The author of the commit is the trigram of the device.
