# fuel — integration

How the frame mounts the fuel module and what the module reads and writes. The rules of the quote are in
[SPEC.md](SPEC.md); the frame's adapter is described in [frame/INTEGRATION.md](../../frame/INTEGRATION.md).

## 2. Mounting (frame loader, `frame/SPEC.md` § 3.2)

The Pilot application lists the module in `frame/app.js` (`{ id: 'fuel', label: Fuel, icon: '⛽' }`, first verb).
`mount(el, ctx)` uses `ctx.data`, `aerodb`, `t`, `lang`, `notify`, `ask`, `askText`, `net` and `identity`; `unmount()`
stops its watchers and observers (a pending write of the current flight or of the settings still leaves). `meta`:

```js
reads: ['planner/', 'pilot/', 'cache/fuel/'],
writes: [
  { prefix: 'planner/flight_performance_database_merged.fpdb.json', merge: 'keyed:profiles:id' },
  { prefix: 'pilot/', merge: 'record' },          // fuel.json and current_flight.json (shared with maps and hello)
  { prefix: 'cache/fuel/', policy: 'cache' }      // last SimBrief OFP, screen and folded blocks: this device only
]
```

- **Title and help (rule 16)**: `meta.title` is the title row (the `h1` draws from it; on a phone the frame puts it in the header
  and clips the `h1`); `ctx.helpAnchor` is called once at `mount()` with a function: Sheets → `fuel-sheets`, a phone (the step bar
  is displayed) → `fuel-step-<n>` of the step shown, a wide module → `fuel-quote`; the anchors are in `help/<lang>.md`.
- The pilot's documents are `pilot/<trigram>/…` (the identity's trigram; `ANON` without identity, as the example
  module does).
- SimBrief: `ctx.net.fetch('https://www.simbrief.com/api/xml.fetcher.php?userid|username=…&json=v2')`, the identifier
  read from `ctx.identity.simbrief`; offline, the frame's 503 `x-sog-offline` gives a warning and nothing else.
- **Weather** (28 Oct 2026, frame INTEGRATION § 14): fuel reads it only through `ctx.weather` — `aloft(samples, when, {
  cacheOnly, stale })` for the winds and temperatures aloft, `metar(ids)` / `taf(ids)` for the corridor's aerodromes,
  `cacheOnly` when the device is offline. No weather host goes through `ctx.net` any more (Open-Meteo, aviationweather.gov,
  metar.vatsim.net, avwx.rest): `ctx.net` is left for SimBrief and the airline's website. `cache/fuel/weather.json` and
  `cache/fuel/aloft.json` are no longer read nor written; the mount removes them once.
- The OFP is kept in `cache/fuel/last_ofp.json` (`put(…, { policy: 'cache' })`): never sent; only its summary goes into
  the current flight.

## 2 bis. Aircraft and sheets through aerodb (since 23 Oct 2026)

`meta.reads: ['pilot/', 'cache/fuel/']`, `meta.writes`: `pilot/` (record) and `cache/fuel/` (cache) only. The aircraft
picker is `(await ctx.aerodb.aircraft()).search(text, 30)`, the choice `aircraftOf(hit)`; the Sheets screen only reads
`sheets.list()` (read-only since 30 Oct 2026: Fuel never calls `sheets.put` / `sheets.remove`; its links open
`?app=maintenance#aircraft?sheet=<id>`, `?app=maintenance#aircraft` for a creation); the sheets logic is
`aircraft().lib` (AeroDBSheets), configured by aerodb (types, sheets, fleet) and by fuel for the active sheet and the
texts. A change of the registry (`aerodb.on('change')` with `aircraft`) reloads the list.

## 3. The current flight — `pilot/<trigram>/current_flight.json`

One record per pilot, read and written by fuel and maps (the same flight in both). Merge rule `record`: the newest
`updated_at` wins the whole document, so a module always reads it, changes its own fields and writes it back whole.

**Who writes what** (`frame/lib/current_flight.js`, `merge(stored, mine, { fields, progressKeys, by })`): every writer
reads the record just before writing and replaces only its own fields; `by` is the writer, never copied from another.
`progress` is shared: each writer replaces only its own keys in it. **`progress.actual` belongs to the frame**: fuel,
report and maps never write nor erase it.

| Writer | Fields | Keys of `progress` |
|---|---|---|
| fuel | `FUEL_FIELDS`: `aircraft`, `route`, `level`, `wind`, `windSource`, `isaDev`, `profile`, `quote`, `weather`, `ofp`, `started`, `planned_at` | `FUEL_PROGRESS`: `at`, `plannedPos`, `eta`, `fuelRemainingKg`, `remainingNm`, `phase` |
| maps (Edit mode of the Map) | `route` (merged into it: `procedures` kept while `dep` / `arr` are unchanged, `wind` removed from the points it moved), `level` | — |
| report (report saved) | `started` (null) | `FUEL_PROGRESS` cleared |
| frame | — | `actual` |

`progress: null` from a writer clears its keys only; `progress` becomes null when nothing is left (no `actual`).

```json
{
  "schema": 1,
  "updated_at": "2026-10-22T14:05:00Z",
  "by": "fuel",
  "aircraft": { "sheetId": "SB_C30J_F-RAJA", "type": "C30J", "registration": "F-RAJA", "name": "C-130J" },
  "route": {
    "text": "LFRS 47.1569 -1.6078,\nN0236F270,\nLUGEN 46.5833 -1.2000,\nLFML 43.4367 5.2150",
    "dep": "LFRS", "arr": "LFML", "altn": "LFPG",
    "points": [{ "id": "LFRS", "lat": 47.1569, "lon": -1.6078 }, { "id": "LUGEN", "lat": 46.5833, "lon": -1.2, "alt_ft": 29000 },
               { "id": "LFML", "lat": 43.4367, "lon": 5.215 }],
    "distanceNm": 366, "trackDeg": 125
  },
  "level": { "ft": 27000 },
  "wind": { "dirDeg": 270, "speedKt": 30 },
  "isaDev": 0,
  "planned_at": "2026-10-25T09:40:00Z",
  "profile": { "climbFpm": 1230, "climbKt": 196, "descentFpm": 1500, "descentKt": 253, "tocNm": 48.2, "todNm": 56.1 },
  "ofp": { "date": "2026-10-19T13:44:06Z", "dep": "LFRS", "arr": "LFML", "altn": "LFPG", "points": 11,
           "levelFt": 27000, "aircraft": "S210 F-BHHH", "callsign": "" }
}
```

- `route.text`: read as item 15 (`LFBO N0450F350 DCT TOU UN460 NTS LFRN`) or as the OFP route list (`ID lat
  lon[/N0450F370]` entries separated by commas or new lines). Fuel writes it **normalised** (23 Oct 2026): one line,
  `DEP PT1 UN460 PT2/F280 … ARR` — identifiers, airways and procedures kept, DCT and speed-level groups dropped, a
  level as `/Fnnn` after the point where it changes, ICAO coordinates as `4530N00030E`. The positions are in `points`
  only: a name aerodb does not know is found again in `points` when the text is read back, so a module that writes
  the text (maps, lot 6) also writes `points`. `distanceNm` and `trackDeg` are derived (great circle, departure to
  arrival track); `from` says where the route came from (`route`, `points`, `ofp`); `manual` true when distance and
  track were typed because nothing resolved.
- `route.points[].alt_ft` (lot C, optional, ft): the level flown **from that point on** (steps); absent = the previous
  level goes on; never on the first or the last point — the flight leaves at `level.ft` and descends to the arrival.
  The same field as maps' mission `route_points[].alt_ft`. Fuel edits the points (order, add, remove, level) and then
  rewrites `route.text` with `textFromPoints` (`frame/lib/route_text.js`): the airway (or procedure) typed between
  two consecutive points is kept while both stay neighbours and unchanged (same name, and same position within
  0.5 NM when the previous points are given), elsewhere the leg is direct (nothing written); levels as `/Fnnn`;
  ICAO coordinates for a point without a usable name. Any module that rewrites the text from points (maps, lot 6a)
  uses the same function, so the airways survive a change made on either side. A module that only reads `points`
  can ignore `text`. Fuel writes the record 300 ms after the last change.
- `route.points[].via` and `awy` (25 Oct 2026, the "Auto" button): `via` is the airway that reaches the point (`"UN460"`:
  the point is read after that airway in `route.text`); `awy: true` marks the nodes of an airway between two points that the
  text does not write (`LFRS TSA01 UT460 TSA05 LFML` has points `LFRS`, `TSA01`, `TSA02*`, `TSA03*`, `TSA04*`, `TSA05`, `LFML`).
  Both are optional and ignorable: the points are the route (distance, line on the map, profile); `text` stays the
  readable form. A module that rewrites the text from the points (`textFromPoints`) writes every point, `awy` ones included,
  and drops the airway name (it only keeps a word between two points that were neighbours in the old text); it must keep the
  points it does not understand. Fuel's reading of the text takes the `awy` points back when the text still holds the same
  airway between the same two points. The airway's path is computed by `frame/lib/routing.js` (maps INTEGRATION § 9);
  fuel's `meta.files` lists it.
- **A flight written by another module** (`by` ≠ `fuel`: maps, lot 6, the route changed on the map; contract of
  23 Oct 2026): fuel, when it sees such a record (watch while mounted, or at its next mount), keeps the route as
  written — `points` and `text` are neither read again nor normalised —, derives `distanceNm` and `trackDeg` from the
  points, redoes the quote and writes the record back with a fresh `profile` and `by: 'fuel'`. Until then the writer
  treats `profile.tocNm` / `todNm` as stale. The writer writes `points` together with `text` (the positions are only in
  `points`).
- `profile` is written by fuel with every quote that changes it (null without a quote): average climb and descent
  rates (ft/min, from the ground to the level and back) and ground speeds (kt), the distance from departure to the top
  of climb (`tocNm`) and from the top of descent to arrival (`todNm`) — the quote's own climb and descent, so the four
  values close the profile at the level. The "top of descent" shown in fuel's result is the gradient rule (level ÷
  gradient + buffer), not `todNm`. Maps draws the vertical profile from it and computes its own when it is missing.
  **`profile.path`** (28 Oct 2026, § 10.20): with procedures chosen and read, `[{ nm, ft }]`, the planned vertical path along the
  flown path (`nm` = the cumulative distance of `flownPath`, the only measure): the quote's climb, cruise (and level steps) and
  descent, then each procedure point's altitude constraint (`at` → ft, `max` → at most, `min` → at least, `between` → within) where
  it is tighter, linear between points, the runway thresholds at their elevation (0 ft without it); absent without procedures.
- `route.procedures` (fuel's, optional, **v2** since 28 Oct 2026, V3_SPECIFICATION § 10.20): the runway, SID, STAR and approach
  chosen in the preparation, as identifiers of the common schema of aerodb (`frame/aerodb/SPEC.md` § 5 quinquies):
  `{ dep: { rwy, sid, trans }, arr: { rwy, star, trans, app, appTrans }, by: 'fuel', at }`. `rwy` is a runway number (`"03"`,
  `"13R"`), the others are procedure identifiers (`LFRS.SID.NTS1A.RW03.NONE`; `trans` / `appTrans` the identifier of the
  transition record); `null` = « aucune », the pilot's own choice; a field absent = not chosen; `at` is the ISO time of the
  choice (`merge` sets `updated_at` on the record). **Fuel is the only writer** (rows of the step Route, the arrival row of
  the step Departure, "Load my OFP"); the Map and every reader read it **only through `proceduresOf(flight)`**
  (`frame/lib/current_flight.js`), which returns the v2 view, migrates the old `{ sid, star }` (objects of the last OFP) and
  returns `{}` (not chosen) for a side whose aerodrome no longer matches `route.dep` / `route.arr`. Migration: nothing is
  written at mount; the v2 shape is written with fuel's next ordinary write, which also drops such a side. "Load my OFP"
  proposes the OFP's SID and STAR (the records `aerodb.rememberOfp` keeps, runway only when the record has a single one) for the
  sides the pilot has **not chosen yet** (absent = not chosen; `null` = "aucune" is a choice) and never replaces a choice; it says
  what it filled, one line per side filled (challenge of 29 Oct, V3 § 10.20).
- `route.points[].wind` (fuel's, lot F): `{ dirDeg, kt, tempC, levelFt, at }` — the forecast wind and temperature
  at the level flown at that point (the plan's, or the step's), from Open-Meteo (`at`: the forecast hour, ISO). Maps
  draws the arrows from it. Absent without a forecast for this route; rewritten whenever the route, the level or
  the flight hour changes.
- `windSource` may also be `{ kind: 'aloft', model, levelFt, at }` when the quote's wind is the mean aloft.
- **`planned_at`** (fuel's, 24 Oct 2026, relay cloud; optional, schema number unchanged, merge rule unchanged): the
  flight date, the planned departure date-time, **ISO 8601 UTC** (`2026-10-25T09:40:00Z`); absent or `null` = now. It is
  the **one value** of the flight date: the "Flight date" field of fuel's step 1 writes it at every change (typed, "+30",
  "Now" = `null`), and everything that depends on the hour follows it — the aerodromes' weather (TAF when the date falls in
  its validity, METAR otherwise, § 10 of the SPEC), the winds and temperatures aloft of the quote (`winds.js`, the forecast
  hour nearest to it, § 11) and, for a flight that is not started, the Map's ETA. A started flight is read from `started.at`
  (fuel resets `planned_at` to `null` when it starts: the start redoes everything for now). **Atmosphere (its session
  reads this): the slider's origin is `planned_at` of the current flight** — "now" when it is absent — and the slider adds
  its 0 to +72 h to it. **Since 28 Oct 2026 fuel no longer writes `weather.when`** (the former copy in the device's
  time): `planned_at` is the only value; a flight written before it gets its `planned_at` from `weather.when` when fuel
  reads it, and the copy is then dropped. A reader that still falls back on `weather.when` finds it absent (= now).
  The field shows `planned_at` in the device's local time and says so in its label.
- `weather` (fuel's): `{ real (wind from the aerodromes' weather) }` (`when`, the former copy of the flight date, is no
  longer written: `planned_at` above; `mid`,
  the former intermediate aerodrome, is no longer written nor read: the corridor's aerodromes replace it); `windSource`: `{ kind: 'weather', ids: ['LFBO (TAF)', …] }` when the wind came from it, else
  null.
- `quote` (fuel's): `{ block, trip, unit ('kg' | 'lb', the sheet's), minutes, levelFt, approx, taxiMin, distanceNm, legs, legsAt? }` — the quote's
  block fuel and trip, rounded, rewritten with every quote that changes them (null without a quote with fuel); Report
  fills "fuel at start" with `block`. **`legs`** (28 Oct 2026, for the recoded Map): `[{ id, min, origin }]`, one per point of
  the flown path in order — `flownPath(expandedPath(flight, procs))` when procedures are chosen (§ 10.20), the route's own points
  otherwise —, `origin` = `'route'` | `'sid'` | `'star'` | `'app'` (a leg written before the procedures has none: read as
  `'route'`), `min` = minutes from brake release (taxi apart: the quote settings' `taxiMin`) to that point, to a tenth
  — the quote's own timetable (climb, cruise by leg with its wind, descent; `progress.js` `plan` / `etas`), the departure
  at 0; `null` without a route of two points or more. **`distanceNm`** (28 Oct 2026): the length the quote ran on, to a tenth
  — the last point's `nm` of the flown path, the route's distance without procedures; it does not change when procedures
  change after the start. **`legsAt`** (ISO, only after the start): when `legs` (and `profile.path`) were last rewritten.
  A reader gives `legTimes` / `etaOf` / `plannedPositionAt` the same `{ path }` as the one the legs follow. **`taxiMin`** (28 Oct 2026): the taxi minutes the quote counts
  (the quote settings' `taxiMin`), written beside `legs`: the frame's helpers (`etaOf`, `plannedPositionAt`) add it to
  `started.at` / `planned_at` before `legs` (fallback 10 min without it).
- `progress` (fuel's, lot H): `{ at, fuelRemainingKg, remainingNm, phase ('taxi' | 'climb' | 'cruise' | 'descent' |
  'arrived'), actual? }` — the started flight's planned fuel remaining, distance remaining and phase, written at most
  once a minute while it flies (at once on a phase change, a cancelled start or a quote change) — a frame write (the
  real position) causes no fuel write; fuel's keys cleared once the start is cancelled or the report saved. **Rule:
  `progress` is a started flight's; readers test `started.at`, never the presence of `progress`** (a `progress.actual`
  kept from an earlier flight says nothing about this flight being in the air). **The ETAs and the planned position are
  derived values** (since the recoded Map, 28 Oct 2026; the debts of that day are lifted): every reader computes them
  with `frame/lib/current_flight.js` — `etaOf(flight, now)`, `plannedPositionAt(flight, now)`, from `quote.legs`,
  `quote.taxiMin` and `started.at` or `planned_at` (`isStarted`, `refTime`, `legTimes`); fuel writes neither
  `progress.eta` nor `progress.plannedPos` any more (nor the ETAs of a flight that is only dated), and its next write
  removes those a previous version had left. My flights and Report show neither.
  `actual` (the real position: phone GPS, IVAO / VATSIM network) belongs to the frame; fuel and report keep it as
  written (table above).
- `started` (lot G): `{ at (ISO), by: 'fuel', diverted? }` — written by fuel at the start (after the weather and the
  quote were redone for now) and set to null by fuel when the start is cancelled, by report when the report that took
  the flight up is saved (the normal end of a started flight); `at` is the report's engine start; when the pilot pressed "Start the flight" on the
  Departure step; Report takes the flight up from there. Absent until then; `null` once the departure aerodrome
  changes (another flight; null rather than absent because writes merge with the stored record); `diverted: true`
  when the arrival changes after the start.
- Levels shown anywhere in the suite: `formatLevel(ft, transitionFt = 5000)` of `frame/lib/route_text.js` — "FL060"
  from the transition altitude, "3 500 ft" below (the airline's transition altitude when it has one).
- `windSource` `{ kind: 'aloft', model, short, levelFt, at }`: `short` is the model's short name (ARPEGE, ICON,
  GFS) shown in "wind: ARPEGE forecast FL060".
- Addresses: fuel opens the map with `#maps?from=fuel` (phone) or `#fuel?with=maps` (dual view, from 980 px); the
  Map's "Edit the route" comes back with `#fuel?from=maps&focus=route` (step 2, route field focused).
- Query read by fuel: `focus=route` (above) and, since 24 Oct 2026, `view=sheets` (`#fuel?view=sheets` opens the Sheets
  screen). Without it the module always opens on the Plan screen (the first tab, "Quote"), whatever the last screen used: `cache/fuel/ui.json` no
  longer holds `view`.
- The Quote / Sheets switch of the module writes the address with `history.replaceState` (`?view=sheets` for the Sheets, no `view` for the
  Quote; other keys kept; no navigation, no new mount), so the frame's popover marks Carburant or Fiches. A `mount()` whose address changed
  while it was reading writes nothing (its state object is its token, `unmount()` invalidates it).
- `aircraft` (fuel's, from `aircraft().aircraftOf(hit)`): `{ sheetId, type, registration, callsign, name, source }`
  (`source`: `sheet`, `fleet`, `reference`, `type`, `free`); report takes the registration and the callsign.
- `wind` is null when unknown; `ofp` is null without a SimBrief flight plan (summary only: the OFP itself stays in the
  device cache).
- Maps reads it as is; a field a module does not know is kept when it writes the record back.

## 4. Quote settings — `pilot/<trigram>/fuel.json`

`{ "schema": 1, "updated_at", "taxiMin": 10, "reserveMin": 30, "contingencyPct": 5, "displayUnit": "kg",
"displaySpeed": "kt", "displayAlt": "ft", "displayDist": "NM", "goal": "prof", "isaDev": 0, "wxRadiusNm": 10,
"entries": { "<sheetId>": <cruise kg/h for this flight> } }` (record). `isaDev` is the last ISA deviation chosen (typed
or taken from the departure METAR); a current flight without `isaDev` starts from it. The three `display…` fields are screen
settings (`kt` | `kmh`, `ft` | `m`, `NM` | `km` | `SM`; absent or unknown: the model's unit); they never change a value
written to `current_flight.json` or to the sheets, which stay in kt, ft and NM.

## 5. Using the model

```js
const M = window.FuelModel,
  sheet = M.normalizeSheet(structuredClone(record)),
  A = await ctx.aerodb.aircraft(),
  apd = A.perf(sheet.icao || sheet.type || sheet.id),
  source = M.cruiseSource({ sheet, altFt, entryKg, apd, simbrief: apd?.simbrief, estimate: A.estimate([sheet.type, sheet.icao, sheet.id]) }),
  perf = M.perfModel(sheet, source, { apd, db: { [code]: { description: A.record(code)?.description } }, dIsa }),
  q = M.quote({ sheet, source, perf, apd, distanceNm, levelFt, trackDeg, wind, taxiMin, reserveMin, contingencyPct });
// level decision and climb instructions (o: the climb IAS of the model sheet, the manual settings, the RPM table)
const L = window.FuelLevels,
  o = { profileIas: +M.modelSheet(sheet, source, apd).climb.iasKt || 0, manual: L.manualSettings(perf, sheet), curve: sheet.rpmFuelCurve },
  goal = L.goalNow(chosenGoal, o.profileIas),
  // every level of the series is a flat flight (quoteAt(h): M.quote with steps: null); the plan's real quote is D.plan
  decision = L.requoteSeries(L.decisionSeries(perf, { distanceNm, wc: q.wc }, goal, o), quoteAt, { h: levelFt, quote: q }),
  climb = L.climbGuide(perf, levelFt, goal, o);
```
