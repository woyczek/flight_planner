# Sortable lists and tables — survey and mock-up (SOG-0498)

Mock-up: `tri_registre.html` (three buttons at the top: default sort, sorted by duration, phone with the sort panel open) and the captures `tri_registre_{defaut,duree}_1280.png`, `tri_registre_{defaut,panneau}_390.png`. The missions are invented. Address on the workstation: `http://127.0.0.1:8000/frame/help/maquette/tri_registre.html`.

## What exists today (survey, file:line of the V3 sources of 18 Nov)
- **Only ONE sortable table in V3**: the coverage table of Data (`modules/data/covtable.js`, state `S.cov.sort = { key, dir }` in memory, `<th scope="col" aria-sort>` with one button per column, text ascending first, numbers descending first, arrows by CSS on `[aria-sort]` in `data/screen.js`). It is the reference.
- **Everything else has a FIXED order and no sort**: the missions registry (`<details>` rows, found first, then problem / read / not read, then series, then id; `REG_ROWS = 60` then « N autres »), the missions list, « Mes vols » (6 grid columns ≥ 980 px, 3 on a phone, newest first), the fleet (by registration, 7 then « N autres »), the Data inventory, the recette and roadmap lists, Settings devices and tokens, « Mes signalements » (groups by priority, 7 per group). Fuel and Atmosphere only have small static tables.
- **Statistics: no screen yet** in V3 (`modules/stats` has only `phases.js`, `journals.js`): it is a future consumer, not a migration. The V2 pages (landing dashboard, Mes vols) have their own sorting (`shared/mission_table.js`, `shared/app_framework.js sortableTable`), not importable by V3.
- **Duplicates to merge**: the « id descending » order is copied six times in `modules/missions/module.js` and `editor_view.js`; the sheet-name sort twice (aircraft, fuel); « sans valeur en dernier » is ad hoc (`1e9`, `9e15`); accent folding in two places; **no `Intl.Collator`, no stable-sort helper, no persistence of a sort anywhere**. No shared table helper in `frame/lib`.
- **Rules that apply** (`frame/design/SPEC.md`, `frame/SPEC.md`, V3 § 7.1): a table is `.f-table` in `.f-scroll`, numbers `.f-num`; targets ≥ 44 px (the coverage table lowers them to 32 px: to settle); no horizontal scroll at 375 px; § 7.1 « filters as chips with a sort button at the end ».

## The proposal (the smallest common block, `frame/lib/sortlist.js`)
- **Columns**: `{ key, label: [fr, en, de, es], type: 'text' | 'number' | 'date' | 'duration', get(row), first: 'asc' | 'desc', emptyLast: true }`. Default first direction: text ascending, number / date / duration descending (as `covtable.js`).
- **State**: `{ key, dir }`, kept by the caller (a module writes it through `ctx.data` with the `cache` policy, as « Mes vols » keeps its view); a default state per list.
- **`sortRows(rows, cols, state, lang)`** → a new array: text with `Intl.Collator(lang, { numeric: true, sensitivity: 'base' })` (accent- and case-blind, « M-10 » after « M-9 »), numbers and durations numerically, dates by `Date.parse`; **an empty value is ALWAYS last, in both directions**; ties keep the original order (explicit stable), then the first column. `nextSort(state, key, cols)`: the same column reverses, another one starts in its first direction.
- **Wide screens**: a real `<table>`; `<th scope="col" aria-sort="ascending | descending | none">` with ONE button per column (44 px high), the arrow by CSS from `aria-sort` (the rule moves from `data/screen.js` to `frame/design/primitives.css`). The block does not draw the rows: the module gives its own `<tr>` (or `<details>`), one delegated `data-sort` handler redraws only the list zone (`keepScroll`), paging (« N autres ») applies AFTER the sort.
- **Phone (≤ 700 px)**: the same rows as a list and **one** « Trier : Durée ▼ » button that opens a small panel — a radio per column and two buttons « Croissant / Décroissant » (44 px, no horizontal scroll). `aria-sort` is valid only on a real column header, so the panel carries `aria-expanded` / `aria-pressed`.
- **First migrations**: (a) the Data coverage table, already conforming, becomes the reference (its tests of `sortCoverage` stay); (b) the missions registry: today it has no columns, it gets the sort control above `[data-regrows]` and a default state `{ id, desc }`, the « not found / problem / not read » grouping kept as the DEFAULT sort only (Features SOG wires it, they offered). Statistics use it when their screen exists.

## Decisions to take (the ergonomist)
1. Wide registry: a **table** with sortable headers (as the mock-up), or keep the folded `<details>` rows and add only the sort bar? The table shows more at once; the rows lose their unfolding (the unfolded body — path, gestures Brief / Atelier / Dupliquer / ⋯ — would move to a row action or a side sheet).
2. The registry's default order (found first, then problem / read / not read): kept as the default sort, or replaced by « Identifiant ▼ » like the mock-up?
3. Is the chosen sort KEPT between visits (per device), or reset at each opening? Proposal: kept per list, reset by a « Remettre l'ordre » entry of the panel.
4. 32 px buttons of the coverage table under a fine pointer: raise them to 44 px (proposal), or keep the dense table for that one screen?
