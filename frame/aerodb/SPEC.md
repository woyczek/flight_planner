# aerodb — specification (regeneration prompt)

This document describes the V3 aeronautical database completely enough for a developer or a language model to rebuild
it without seeing its code. The reference implementation is `frame/aerodb/aerodb.js` (SIA base, queries, provisional
reader), `frame/aerodb/aircraft.js` (aircraft types) and `frame/aerodb/zones.js` (zone frames, generated by
`tools/build_aerodb_zones.py`). How the frame mounts it and how a module uses it: [INTEGRATION.md](INTEGRATION.md).
Choices and measurements: [DECISIONS.md](DECISIONS.md).

**How to use this document as a prompt.** Ask for three plain JavaScript files (no ES module syntax, no dependency, no
DOM, no interface text) that define `window.AeroDB`, `window.AeroDBAircraft` and read `window.AERODB_ZONES`. Every rule
below is a requirement; section 6 (invariants) always wins.

## 1. Purpose

Every module of the suite (maps, fuel, report, later CPCO) needs aeronautical data: airspaces, aerodromes, beacons,
points, airways, VFR reporting points, obstacles, MORA, air refuelling tracks, NAT tracks, towns, and the aircraft types
with their performance. aerodb answers those questions from the bases **published** to the data repository by a
workstation with the launcher. It never reads the source files (AIXM, XML_SIA, openAIP…), never builds, never writes.
A module asks for an area or an identifier, never for a zone or a file.

## 2. What it reads

- **SIA base, split format (preferred)**: one file per zone, cycle and kind,
  `sia/base/<zone>/<cycle>/<kind>.json` = { `schema: 2`, `zone`, `cycle`, `kind`, `parserVersion`, `data`,
  `updated_at` }. Kinds and their `data`: `airspaces`, `aerodromes`, `navaids`, `points`, `vrp`, `airways`,
  `obstacles` (arrays), `mora` (cells [{ lat, lon, mora, moraFt, latStep, lonStep, … }]), `obstaclemax`
  ({ "lat|lon": ft }), `cities` (the zone's towns [{ name, lat, lon, population, … }]: those of its country in
  GeoNames, or, for a country without a zone, those inside its contour) and `meta` (everything else:
  `aarXml`, `aarXmlExtra`, `natTracks`, `airac`, …). Next to them:
  - `aeroindex.json`, the light index of the zone's aerodromes with an ICAO code (written by the publication of the
    base, `shared/sia_base.js`, from the next publication on): `data` = { `fields`: [`icao`, `name`, `lat`, `lon`,
    `elev`, `bearing`, `magVar`], `rows`: [[…], …] } (France: 555 aerodromes, 31 KB, against 328 KB for
    `aerodromes.json`). Read, when the zone has one (tree listing or manifest sizes), to find an aerodrome by its code
    (`coords`, `coordsAll`, `aerodromes({ icao })`) and for `aerodromes({ bbox, lite: true })`; its items carry
    `lite: true` and no type, state nor hard runway. Everything else (the map's symbols, `find`) reads
    `aerodromes.json`. Without the index (a base published before), `aerodromes.json` as before;
  - `sia/base/cities_major.json` { `data`: towns of 100,000 inhabitants or more, the whole world }, for a place search
    outside the loaded zones;
  - `sia/base/index.json` { `zones`: { zone: { `cycle`, `prefixes` (first two letters of its aerodromes' ICAO
    codes), `kb` (size of each file), `cells` } } }, the manifest. `cells` lists the one-degree cells the zone's data
    cover, as longitude ranges per latitude row: { "43": [[-10, -2], [0, 4]], … }. A cell is covered when:
    - it holds a point (aerodrome, navaid, point, VRP, obstacle) or a MORA cell;
    - an airway passes through it (sampled every 0.25°);
    - an airspace's outline crosses it, or its centre is inside the airspace.
- **SIA base, whole format (V2, read during the transition)**: `sia/base/<zone>/<cycle>.json`, one active zone
  (`schema: 1`, `airspaces`, `aero` { `aerodromes`, `navaids`, `points`, `airways`, `vrp`, `obstacles` },
  `obstacleMax`, `moraCells`, `aarXml`, `aarXmlExtra`, `natTracks`, `airac`, …), towns in `sia/base/cities.json`
  { `cities` } for the whole world.
- In both formats airspace rings are `[[lat, lon], …]`; points carry `lat`, `lon`, `id` (aerodromes `icao`), airways
  carry `a` and `b` ends. Zone ids are those of `AERODB_ZONES`, plus `nat` (oceanic).
- **Aircraft types**: `AircraftDB/aircraft_db.json` and `aircraft_perf.json`; when absent, the V2 files
  `aircraft_db.js` and `aircraft_perf.js` (`window.AIRCRAFT_DB = {…};`) read as a JSON literal — never executed.
- **VFR reporting points of the VAC charts** (§ 5 quater): `sia/vfr/<ICAO>.json`, one file per aerodrome, and
  `sia/vfr/index.json`, read on demand.
- **Zone frames**: `AERODB_ZONES` { id: { n: [fr, en, de, es], b: [[west, south, east, north], …] } }, one frame per
  part of the zone, generated from the zone contours of the suite.

## 3. Reader

aerodb reads files only through a reader with the frame's data contract:

- `read(path, { policy: 'reference', wait: true })` → `{ value | text, rev, cached, at }`, or `null` when the file is
  absent (or offline without a copy). `value` is the parsed JSON; otherwise `text` is parsed. `rev` is opaque: compare
  revisions only with each other.
- `list(prefix)` → paths, or `null` when no listing is known (launcher without a listing, first launch offline).
- `watch(prefix, fn)` (optional) → called with the changed paths after a synchronisation. The frame's data layer
  also calls it when a file first arrives in its cache. aerodb therefore reacts only to two cases:
  - a file it has already read whose `rev` changed: the zone, or the towns, manifest or aircraft base, is forgotten
    and read again on the next question;
  - a cycle or zone missing from the listing it holds: the listing is read again.
  A `change` event is sent only in those cases.
- For the offline data API (§ 5, `offline`), two more calls, both local and without network:
  - `cached(prefix)` → `[{ path, rev, bytes, at }]`: the local copies under a prefix;
  - `evict(path or prefix/)`: drops the local copies of reference files, never queued, never sent.
  The frame's adapter offers both (frame lot 6). With a reader that lacks them, `offline.supported()` says so, states
  are `unknown` and `release` throws.

Until the frame delivers its data layer, `AeroDB.fetchReader()` stands in. In GitHub mode it reads through
`GitHubData` (contents and tree). Otherwise it reads the files served by the launcher (`data/<path>`, `AircraftDB/` at
the suite root) and has no listing.

## 4. Rules

- **Published zones.** From the reader's listing (a split cycle counts when its `meta.json` is listed), otherwise
  from the manifest `sia/base/index.json`, otherwise unknown.
- **Cycle.** When the published zones are known, take the most recent cycle already in force (its date is not after
  today), otherwise the oldest one (published in advance). When they are unknown, try the AIRAC cycle in force, then
  the five before it (28-day cycles from 25 January 2024 = AIRAC 2401); the first file found wins.
- **Missing zones.** A zone with no file is remembered as missing until the next change, but only when nothing says it
  is published. A published zone that cannot be read (offline, not kept) is asked for again at the next question.
  Likewise, a kind that could not be read answers empty this time and is read again next time.
- **Format.** For the chosen cycle, the split format is preferred (its `meta.json` exists), otherwise the whole file is
  read.
- **Zones of an area.** A zone is concerned when its data touch the area: one of its manifest `cells` is under the
  area.
  - A zone without `cells` (old manifest, or no manifest at all) falls back to its frames from the table, widened by
    half a degree for coasts and territorial waters. A country's frame overflows it: Spain's covers the south of
    France.
  - With a listing, only published zones count.
  - When nothing touches the area, the published zones with neither cells nor frame (oceanic) are taken.
- **Loading.** Split format: opening a zone reads only `meta.json`; each kind is read once, on the first question
  that needs it (a module asking for aerodromes reads `aerodromes.json` and nothing else). Whole format: the zone is
  read once. Concurrent questions share the same read.
- **Indexes.** Built per zone and per kind on the first question of that kind, in memory, by one-degree cell
  ("floor(lat)|floor(lon)"):
  - points (aerodromes, navaids, points, VRP, obstacles): the cell of the point;
  - airspaces: every cell of their frame; an airspace covering more than 400 cells (FIR, UIR) goes to a "wide" list
    checked on every question;
  - airways: the cells of the segment's frame, up to 64, otherwise the cells of both ends;
  - MORA: one cell per position; identifiers: aerodrome ICAO code, beacon, point and VRP ids.
- **Area questions.** Given `{ bbox: [west, south, east, north] }` or `{ lat, lon, radiusNm }`, visit the cells of the
  area when they are fewer than the index's cells, otherwise the index's cells filtered by the area, so that a whole
  world question is as fast as a large one. Results are exact (filtered by position or frame), without duplicates
  across zones.
- **MORA.** The cell containing the point; `moraFt`, otherwise the "3⁵" notation read back (superscript = hundreds).
- **Identifiers.** For a four-letter code, first the zones whose manifest lists its two-letter prefix, then the
  loaded zones, then the published zones one by one until it matches. `coords` prefers an aerodrome.
- **Towns.** Area questions use the towns of the zones covering the area. Name questions (`find`, `cities` by prefix)
  use the towns of the loaded zones and the world's major towns. Whole format: the world's towns.
- **Place search.** Rank: exact code; aerodrome with an ICAO code whose name starts with the text; town (most
  populated first); other place whose code or name starts with the text; then those containing it.
- **Aircraft types.** Aliases followed to the end (A4M → A400M → A400); the classification rules, the usage names
  (RAFALE → RFAL, H145 → EC45), the display name and the cruise fuel estimate (named type, then ICAO class and wake
  category) are those of the V2 suite. Type search ranks: designator starting with the text, alias or usage name
  starting with it, a word of the model starting with it.
  - **Helicopters** (ICAO class H… or G…, or a helicopter type): `estimate` adds `category: 'helico'`, a practical
    ceiling (piston 12,000 ft, single turbine 16,000, twin turbine 20,000; Airframe DB's ceiling only when lower — it
    gave 27,926 ft for an H145) and `ecoFt: 3000`, the low economical cruise level fuel takes for a helicopter; without
    a named type, fuel flow and speed by maximum mass (1.5, 3, 4, 7.5, 12 t bands). Other aircraft get `category` too.

## 5. API

`AeroDB.create({ reader, zones, now })` → service:

| Call | Answer |
|---|---|
| `status()` | `{ published: { zone: cycle } \| null, source: 'list' \| 'index' \| 'none', loaded: { zone: cycle }, missing: [zones], cycle }` (a zone read in the whole format shows "(whole)") |
| `state()` | `{ state, asked, zones?, loading? }` without reading anything: `loading` (the list of published zones or a zone is being read; `loading`: the zones), `ready`, `noaccess` (nothing to read the base with on this device: `create({ access })` says so), `offline`, `unpublished` (the access works, nothing published), `idle` (never asked). A module words the three that mean a missing base differently: loading, access not set, not published. `on('state', fn)` follows it; `refresh()` reads the list again (access changed, network back); an empty list is also read again after 30 s, at the next question |
| `ready(q)` | zones loaded for the area of `q` |
| `on('change', fn)` | `fn({ zone, cycle } \| { changed } \| { aircraft })`; returns the unsubscribe function |
| `airspaces(q)` | airspaces touching the area; `q.types` keeps some types |
| `aerodromes(q)` | aerodromes of the area, or the one of `q.icao` (from the light index when published); `q.lite`: the area's aerodromes with an ICAO code from the light index (code, name, position, elevation, runway axis, magnetic variation) |
| `navaids(q)`, `points(q)`, `vrp(q)` | points of the area |
| `obstacles(q)` | obstacles of the area; `q.minHgt` (ft) |
| `airways(q)` | airways with a segment touching the area |
| `mora(lat, lon)`, `moraCells(q)` | MORA of a point (ft, or null), cells of an area |
| `aar()`, `nat()` | refuelling track files (XML) of the loaded zones, NAT tracks of the day |
| `aarTracks()` | the refuelling tracks of the loaded zones ready to draw (`aar.js`, taken over from `shared/aar_tracks.js`): `[{ name, kind: 'track' \| 'heavy', heading, lengthNm, widthNm, side, ip, cp, ring (racetrack outline) \| legs }]`; built again only when the zones' XML change |
| `natTracks()` | NAT tracks of the day with their points placed: `[{ id, points: [{ id, lat, lon }], west, east (levels), from, to, by }]`; a named point through `coords`, "61/20" or "6130/20" as degrees north and west; an unknown name is left out |
| `vfrRoutes(icao)` | VFR reporting points, sequences and instructions of an aerodrome extracted from its VAC charts (§ 5 quater), or null |
| `procedures(icao, q)`, `procedureIndex()`, `procedureFromOfp(ofp)`, `rememberOfp(ofp)` | SID / STAR / approaches at the common schema (§ 5 quinquies) |
| `vfrIndex()` | the aerodromes of the VFR compilation with their counts, or null before any import |
| `cities(q)` | towns of the area, or by `q.prefix` (most populated first), `q.n` at most |
| `find(text, n)` | ranked places: `{ label, lat, lon, name, kind, code }` |
| `coords(ident)`, `coordsAll(ident)` | position of an identifier; every place carrying it |
| `aircraft()` | the aircraft registry (§ 5 bis): the types (`canonical`, `related`, `record`, `classify`, `codeOf`, `displayName`, `label`, `perf`, `estimate`, `searchTypes`, `size`) and `search`, `resolve`, `aircraftOf`, `sheets`, `fleetTypes`, `lib` (AeroDBSheets) |
| `stats()` | per loaded zone: cycle, format, MB read, each file read (kind, KB, ms), indexes built |
| `offline.supported()` | `{ cached, evict }`: what the reader allows |
| `offline.zones()` | published zones, by name: `{ id, names: [fr, en, de, es], prefixes, cycle, format, publishedKb, cachedKb, state, at, staleKb }`; `state` is `absent`, `partial`, `complete` or `unknown`; `at` is the date of the newest local copy; `staleKb` counts the copies of other cycles |
| `offline.keep(zone, { onProgress })` | reads every kind of the zone's cycle, plus the common files (manifest, major towns), into the frame's cache; `onProgress({ done, total, path, kb })`; returns the zone's state with `failed` (paths) and `readKb` |
| `offline.release(zone)` | evicts the zone's folder (`sia/base/<zone>/`: every cycle, both formats) in one call and closes the zone in memory; common files stay; returns the zone's state |
| `offline.common()` | state of the common files |
| `offline.aircraft()` | aircraft base: `{ files: [{ path, cached, kb }], types, state, cachedKb, at }` (JSON files, or the V2 `.js` when only those are cached) |

Every call is asynchronous except the aircraft base's methods once `aircraft()` resolved.

## 5 bis. Aircraft registry (`registry.js`, `sheets.js`)

All the aircraft data in one place, read from every source and written in one place.

- **Four kinds of entries**:
  - **sheets**:
    - performance sheets, one file each: `aircraft/sheets/<id>.json` (the master; `id` kept in the sheet, file name
      sanitised);
    - V2's `planner/flight_performance_database_merged.fpdb.json` is adopted in reading (origin `v2`), and merged in
      when it is newer on a field;
  - **aircraft**, keyed by registration:
    - the fleet `airline/fleet.json` (written by website), else V2's `references/aircraft_fleet.js`;
    - V2's `references/defa_reference.js` adds the registrations that are absent; bare numbers ("1", "110") are not
      registrations;
    - V2 `.js` files are read as their `let data = {…};` literal, never executed;
  - **types**: the published ICAO base (aircraft.js);
  - **free code**.
  Mission aircraft come through the reference and the fleet only.
- **Origin and date of every field**: `_fields: { path: { at, source } }`.
  - Sources: `edit`, `v2`, `lnmperf`, `chatgpt`, `eurocontrol`, `simbrief`, `ofp`, `import`, `fleet`, `reference`…
  - The newest wins. The losing values are kept in `_kept: { path: [{ value, at, source }] }` (five per field).
  - Rule of V2 kept: the fleet's base stays; callsigns are united.
- **Search**, one for everything: `search(text, n)` returns, in this order, aircraft with a sheet of their own → type
  sheets → fleet → reference → types (two letters at least) → free code (two to four letters or digits). With an empty
  text, the sheets then the fleet.
  - **One line per registration**: an aircraft's own sheet, its fleet entry and its reference entry make a single
    line; its fields are merged, the sheet first (`origin: { type, callsign, name, sheet }` says where each came from;
    `sources` lists them).
  - Each result: `{ kind, source, key, label, sheetId, sheetVia, ownSheetId, type, registration, callsign, name }`;
    `sheetId` is always the sheet that gives a quote (below).
  - `aircraftOf(result)` gives the current flight's `aircraft` (`{ sheetId, type, registration, callsign, name,
    source }`).
- **An aircraft's sheet for a quote**: its own (same registration) when it gives a quote (a fuel flow: cruise, or a row
  of its RPM table), else its type's that gives one (aliases followed by `related`), else none and `estimate(type)`.
  An incomplete own sheet stays named (`ownSheetId`), so a choice always gives a quote. `resolve(registration)` gives
  the aircraft, its sheet (`sheetVia`: own, type, estimate), `ownSheetId` and the estimate when there is no sheet.
- **Sheets API**, `aircraft().sheets`:
  - `list()`, `get(id)`, `origins(id)` (source, date and kept values per field);
  - `put(sheet, { source })`: the changed fields are stamped and the previous values kept;
    `aircraft/sheets/<id>.json` is written, then the sheet goes into the V2 mirror (`fpdb.json`, without `_fields`
    and `_kept`, with `updated_at` and `updatedAt`);
  - `remove(id)`.
  Writing needs a reader with `put` and `remove` (the frame's adapter); the provisional reader only reads.
- **Merge** of two versions of a sheet (the rule declared to the frame for `aircraft/sheets/`, `mergeSheets`): field by
  field, the newest stamp wins, the loser goes to `_kept`. When the same field has two values, the losing version is
  returned as `lost`, so the frame counts a conflict.
- **Sheets logic** (`AeroDBSheets`, taken over from fuel): reading CSV, JSON, `.lnmperf`, OFP and ChatGPT replies;
  merge with choices; `.lnmperf` writing; EUROCONTROL and SimBrief completions. aerodb configures it with the types,
  the sheets and the fleet (`fleetTypes()`, for the ChatGPT prompt). Registration and callsign are editable fields.
- **Prefixes** (`AeroDB.declaration()`, given by the frame to `FrameData.adapter`):
  - reads: `sia/base/`, `AircraftDB/` and `references/` as "reference"; `airline/`, `planner/` and `aircraft/` as
    documents;
  - writes: `aircraft/sheets/` (merge `mergeSheets`) and the V2 mirror `planner/…fpdb.json` (merge
    `keyed:profiles:id`).
- **Loading**: `aircraft()` loads `registry.js` and `sheets.js` from aerodb's folder at its first call. Everything is
  read in parallel: the two scripts, the types base (`aircraft_db` and `aircraft_perf`: the JSON or the V2 `.js`,
  chosen from the repository's tree when the reader lists it, otherwise both asked at once, the JSON preferred) and,
  as soon as `registry.js` is there, every source of the registry (`AeroDBRegistry.readAll`: the sheets of
  `aircraft/sheets/`, the V2 fpdb, the fleet, the reference, and the V2 fleet only when the tree says
  `airline/fleet.json` is missing), handed to `create({ raw })` and interpreted by the first `load()`. A change under
  `aircraft/`, `airline/`, `planner/` or `references/` makes it read again at the next call, and sends
  `{ aircraft: true }`; changes that are the registry's own first reads do not.

## 5 ter. Little Navmap files kept in step (`lnmperf.js`)

On a workstation served by the launcher, the performance sheets and the `.lnmperf` files of one folder stay the same
both ways.

- **Folder**: set in Settings › "Little Navmap sheets" (a launcher page only), kept by the launcher in
  `tools/.lnmperf.json` (local, never versioned). The data folder is refused.
- **Launcher routes** (`tools/launch.py`, `X-SOG-Setup` header, page served there only):
  - `GET / PUT /__setup/lnmperf-folder`: `{ folder, exists, suggestions }` (the usual Little Navmap folders found);
    `PUT { folder }` (empty: off);
  - `GET /__setup/lnmperf`: `{ folder, files: [{ name, size, mtime, sha }] }` (SHA-1 of the content);
  - `GET /__setup/lnmperf?name=…`: `{ name, text, size, mtime, sha }`; `PUT /__setup/lnmperf?name=…` (text): written
    at once (temporary file, then replace);
  - `POST /__setup/lnmperf?name=…&action=retire`: the file moved to `_removed/` in the folder, never deleted;
  - no folder set: 409; names are a bare `.lnmperf` file name.
- **Manifest** `cache/aerodb/lnmperf.json` (frame cache, this device): `{ schema, folder, files: { name: { sheetId, sha,
  view } } }`. `view` is the sheet's `.lnmperf` fields at the last pass, in the sheet's unit, rounded to the
  thousandth as the file stores them. A new folder starts a new manifest.
- **Comparison** on the fields a `.lnmperf` carries (`LNM_PATHS`: name, type, description, fuel kind, contingency,
  extra, reserve, taxi and usable fuel, runway, and fuel flow, TAS and vertical speed of alternate, climb, cruise and
  descent). A sheet's view is read back from the text it would write, so both sides go through the same rounding.
- **The five cases**, for each file and its sheet:
  1. sheet changed → file rewritten;
  2. file changed → the changed fields go into the sheet (origin `lnmperf`, previous values kept);
  3. both changed → field by field: a field changed on one side only takes that side; changed on both sides with
     different values, the newest wins (the field's date in `_fields` against the file's date), the losing value goes
     to `_kept` (a file value with origin `lnmperf` and the file's date), and one conflict per sheet is counted at the
     frame's synchronisation button (`FrameData.noteConflict`, the file's version as the losing one, which `restore`
     can take back); the file is rewritten when the sheet kept a value of its own;
  4. new file → a new sheet (origin `lnmperf`, id from the file name, made unique); a file named after a sheet that
     has no file yet is merged with it (no common base: every difference is a conflict);
  5. file deleted → rewritten from the sheet.
  A sheet removed: its file goes to `_removed/` if it did not change since the last pass, else it becomes a sheet
  again. A sheet without the fields Little Navmap requires is not written, and is listed. An unreadable file is
  listed, never removed.
- **Units**: a `.lnmperf` holds pounds (or gallons, `FuelAsVolume`). A sheet in kg is converted to pounds when written
  (`toLnmperf`) and back when read; fuel in gallons is never compared with a mass.
- **When**: at start (1.5 s after aerodb, then 4 s), after each synchronisation of the frame (`onStatus`, a new
  `lastSync`), and every two minutes while the page is visible; one pass at a time. Without a launcher or a folder,
  nothing is scheduled. `AeroDB.create({ lnmperf: false })` turns the automatic passes off (tests).
- **API**: `aerodb.lnmperf()` → `{ start, sync, status, on, folder, setFolder, download, card, stop }`:
  - `status()`: `{ state: off | idle | running | error, folder, at, linked, written, imported, merged, retired,
    conflicts, lastConflicts, incomplete: [ids], errors: [{ name, message }] }`;
  - `download(id)`: the sheet as a `.lnmperf` file (a phone, no launcher);
  - `card(el, { t, notify })`: the Settings card (folder, found folders, Save, Synchronise now, Stop, state), the one
    screen aerodb gives (invariant 4).

## 5 quater. VFR reporting points of the VAC charts (`sia/vfr/`)

- **Source**: `tools/report-vfr/` (README.md), run on a workstation over the folder of the VAC PDFs (optional Python
  module `pypdf`, nothing in the app imports it): `refresh_vfr.py` (or `compile_vfr.py`) writes `vfr-compiled.json`.
  Format 1.x (first prototype): `aerodromes[]` with `points`, `routes`, `evidencePages`. Format 2.x: points with `role`
  (`reporting_point`, `aerodrome_reference_point` "AD", `intermediate_waypoint` "MAN-…" placed by a manual analysis) and
  `origin`; named routes (`key`) with `direction` (`forward`, `both`, `unknown`), `runways`, `conditions`, an interpreted
  `geometry` (LineString), `geometryPartial` and `geometryOmission`; written `instructions` by page; the aerodrome's
  `status` (`calculé`, `interprété`, `obsolète`, `sans relations`), `interpretationScope` and `interpretation.notes`.
  Everything is extracted from the VAC, never a published route.
- **Import** (Settings › Maintenance › Aeronautical data, "Import a VFR compilation (VAC)…", Expert level, launcher
  only): the page sends the file to `POST /__setup/vfr-import` (`tools/vfr_import.py`, standard library):
  - strict check first: `schemaVersion` 1.x or 2.x, ICAO codes, point codes (`[A-Z0-9][A-Z0-9-]{0,23}`), coordinates
    `[longitude, latitude]` in range, pages, every code of a sequence or of a geometry known (a point of the aerodrome,
    the aerodrome's ICAO code or "AD"), geometries, directions, text sizes; one error and nothing is written, the first
    20 errors are returned and shown;
  - each reporting point is matched with the base's VRP `<ICAO without its first two letters>-<code>`, or
    `…-H-<code>` for a helicopter point (the VAC writes "HE", the base "MN-H-HE") (latest cycle of
    `sia/base/fr/`, within 0.02°); unmatched points keep their VAC coordinates, `vrp: null`;
  - plan first (summary: aerodromes, points, unmatched points, sequences, pages of instructions, files changed and
    removed, size), then, after agreement, writing of `sia/vfr/`, a commit in the author's name and a synchronisation.
    Files no longer produced are removed; an identical import changes nothing.
  - To redo at each new VAC cycle: run `refresh_vfr.py` again (tools/report-vfr/README.md), then the button.
- **Files**: `sia/vfr/<ICAO>.json` = { `schema: 2`, `ad`, `status: 'candidate'`, `label` ("Extrait des VAC, à
  vérifier"), `analysis` { `status`, `scope`, `notes` } (null fields from a 1.x file), `source` { `file`, `sha256`,
  `cycle` }, `generatedAt`, `points` [{ `code`, `vrp`, `lat`, `lon`, `role`, `origin`, `page`, `text`, `restrictions` (usage read in the VAC:
  "ATC instruction only", "radio communication failure procedure"…), and for a manual vertex `accuracyM` (null when
  not measured) and `accuracyNote` }], `routes` [{
  `key`, `codes`, `vrps`, `pages`, `text`, `fragment`, `status` (`interpreted` or `candidate`), `direction` (from an
  analysis only, else `unknown`), `runways`, `conditions`, `geometry` ([[lat, lon], …] or null), `partial`, `omission`
  }], `notes` [{ `page`, `title`, `text` }] } (the written instructions, else the text of the pages found, one per page,
  titled by the page's first line after the aerodrome's name); `sia/vfr/index.json` = { `schema: 2`, `status`,

  `routes`, `notes`, `unmatched`, `analysis` }] }. A file written by the first version (`schema: 1`, `page` per route)

- **Display rules** (for maps): always dashed, labelled "extracted from the VAC, to be checked"; an interpreted

## 5 quinquies. Procedures (SID, STAR, approaches): `proc/`, `proc-seen/`

- **Principle**: procedures enter the suite through aerodb only, consolidated into one schema whatever the source. A module
  never reads a source; it asks `procedures(icao, q)`. Decisions: DECISIONS 25 Oct 2026.
- **Files**: `proc/<cycle>/<ICAO>.json` and `proc/<cycle>/index.json` (published by the workstation, by AIRAC cycle, read as
  `reference`; the cycle is picked like the base's: the latest in force from the reader's listing, otherwise the first
  recent AIRAC cycle whose file reads), and `proc-seen/<ICAO>.json` (what the user's own OFPs contained, written by
  `rememberOfp`, synchronised with the private data repository, newest record of an id wins).
- **Aerodrome file**: { `schema: 1`, `icao`, `cycle`, `updated_at`, `procedures` [ procedure ] }. **Procedure**:
  - `id`: `ICAO.KIND.NAME.RWnn.TRANSITION` (`RWALL` without a single runway; name and transition without spaces or hyphens);
  - `icao`, `kind` (`SID` | `STAR` | `APP`), `name` (as published or filed), `runways` ([`"23"`, `"05R"`] or [] when the
    source does not say), `transition` (or null);
  - `points`: [ { `seq`, `id`, `lat`, `lon` (WGS84 degrees), `alt` (null or the published constraint { `type`: `at` | `min` |
    `max` | `between`, `ft`, `ft2?` }), `planned` (OFP only: altitude of the plan, ft, never a constraint), `via` (airway or
    null), `leg` (ARINC path terminator IF / CF / DF / TF… when the source has it; absent = straight segment) } ];
  - `source` { `kind`: `simbrief` | `eaip` | `eurocontrol` | `cifp` | `xplane` | `navigraph`, `ref`, `cycle`, `at` };
  - `status`: `official` | `check` ("to be checked") | `ofp` ("seen in an OFP", not authoritative).
- **Merge** (`procedures`): records of the same kind, name and transition with compatible runways (one of the two lists empty,
  or a common runway) are one procedure; the geometry and status are those of the best source (`official` > `check` > `ofp`),
  `sources` lists every source with its status, best first.
- **Calls**:

  | Call | Answer |
  |---|---|
  | `procedures(icao, { kind, runway, name, transition })` | merged procedures of the aerodrome (published cycle + seen in OFPs), filtered; `[]` without data or for a bad code |
  | `procedureIndex()` | `proc/<cycle>/index.json` = { `cycle`, `aerodromes`: { ICAO: { SID, STAR, APP counts } } }, or null |
  | `procedureFromOfp(ofp)` | `{ sid, star }` of a SimBrief OFP (`json=v2`), each a procedure with status `ofp` or null; writes nothing |
  | `rememberOfp(ofp)` | same answer, and keeps both in `proc-seen/<ICAO>.json` (nothing written when the same record is already there); null when the reader does not write |

- **OFP reading**: from `navlog.fix`, TOC, TOD and aerodromes are left out; fixes flagged `is_sid_star` before the first
  unflagged fix are the SID, after the last one the STAR (without any unflagged fix: by `stage`, `CLB` the SID, otherwise the
  STAR); name and transition from `general.sid_ident` / `sid_trans` / `star_ident` / `star_trans`, runway from
  `origin.plan_rwy` / `destination.plan_rwy`, altitude of the plan from `altitude_feet`. The OFP is read one flight at a time:
  aerodb never calls SimBrief and never knows the user name (Fuel's setting). The field names are SimBrief's documented ones,
  to be checked against a real OFP.
- **Test**: `frame/aerodb/test/procedures.html` (14 checks), case K1 of `tests/v3/`.

## 6. Invariants

1. aerodb never writes the SIA base nor AircraftDB, never builds, never executes a file read from the data
   repository. It writes only the performance sheets (`aircraft/sheets/`) and their V2 mirror, and, through the
   launcher, the `.lnmperf` files of the folder set by the user. Keeping and releasing only fill and empty the
   device's cache.
2. A module never names a zone or a file; aerodb chooses them.
3. A question over the whole world returns exactly the published base (same counts as the workstation's base).
4. No interface text: labels, translations and formatting belong to the modules and the frame. One exception: the
   Settings card of the `.lnmperf` folder (§ 5 ter), in four languages, so that the Settings screen does not carry the
   synchronisation's states.
5. ICAO and EUROCONTROL data are never part of the public website.
