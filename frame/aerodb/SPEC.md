# aerodb — specification (regeneration prompt)

This document describes the V3 aeronautical database completely enough for a developer or a language model to rebuild
it without seeing its code. The reference implementation is `frame/aerodb/aerodb.js` (SIA base, queries, provisional
reader), `frame/aerodb/aircraft.js` (aircraft types) and `frame/aerodb/zones.js` (zone frames, generated by
`tools/build_aerodb_zones.py`). How the frame mounts it and how a module uses it: [INTEGRATION.md](INTEGRATION.md).
Choices and measurements: [DECISIONS.md](DECISIONS.md).

**How to use this document as a prompt.** Ask for three plain JavaScript files (no ES module syntax, no dependency, no
DOM, no interface text) that define `window.AeroDB`, `window.AeroDBAircraft` and read `window.AERODB_ZONES`. Every rule
below is a requirement; section 6 (invariants) always wins.

## 1. Purpose

Every module of the suite (maps, fuel, report, later CPCO) needs aeronautical data: airspaces, aerodromes, beacons,
points, airways, VFR reporting points, obstacles, MORA, air refuelling tracks, NAT tracks, towns, and the aircraft types
with their performance. aerodb answers those questions from the bases **published** to the data repository by a
workstation with the launcher. It never reads the source files (AIXM, XML_SIA, openAIP…), never builds, never writes.
A module asks for an area or an identifier, never for a zone or a file.

## 2. What it reads

- **SIA base by zone and cycle**: `sia/base/<zone>/<cycle>.json`, one active zone, plain JSON (`schema: 1`, `zone`,
  `cycle`, `parserVersion`, `updated_at`, `airspaces`, `aero` { `aerodromes`, `navaids`, `points`, `airways`, `vrp`,
  `obstacles` }, `obstacleMax` { "lat|lon": ft }, `moraCells` [{ lat, lon, mora, moraFt, latStep, lonStep, … }],
  `aarXml`, `aarXmlExtra`, `natTracks`, `airac`, …). Airspace rings are `[[lat, lon], …]`; points carry `lat`, `lon`,
  `id` (aerodromes `icao`), airways carry `a` and `b` ends. Zone ids are those of `AERODB_ZONES`, plus `nat` (oceanic).
- **Towns**: `sia/base/cities.json` { `cities`: [{ name, lat, lon, population, … }] }, the whole world today (by zone
  from lot 3).
- **Aircraft types**: `AircraftDB/aircraft_db.json` and `aircraft_perf.json`; when absent, the V2 files
  `aircraft_db.js` and `aircraft_perf.js` (`window.AIRCRAFT_DB = {…};`) read as a JSON literal — never executed.
- **Zone frames**: `AERODB_ZONES` { id: { n: [fr, en, de, es], b: [[west, south, east, north], …] } }, one frame per
  part of the zone, generated from the zone contours of the suite.

## 3. Reader

aerodb reads files only through a reader with the frame's data contract:

- `read(path, { policy: 'reference', wait: true })` → `{ value | text, rev, cached, at }`, or `null` when the file is
  absent (or offline without a copy). `value` is the parsed JSON; otherwise `text` is parsed. `rev` is opaque: compare
  revisions only with each other.
- `list(prefix)` → paths, or `null` when no listing is known (launcher without a listing, first launch offline).
- `watch(prefix, fn)` (optional) → called with the changed paths after a synchronisation.

Until the frame delivers its data layer, `AeroDB.fetchReader()` stands in. In GitHub mode it reads through
`GitHubData` (contents and tree). Otherwise it reads the files served by the launcher (`data/<path>`, `AircraftDB/` at
the suite root) and has no listing.

## 4. Rules

- **Cycle.** With a listing, each zone's cycles are known: take the most recent cycle already in force (its date is not
  after today), otherwise the oldest one (published in advance). Without a listing, try the AIRAC cycle in force, then
  the five before it (28-day cycles from 25 January 2024 = AIRAC 2401); the first file found wins. A zone with no file
  is remembered as missing until the next change.
- **Zones of an area.** A zone is concerned when one of its frames, widened by half a degree (coasts, territorial
  waters), touches the area. With a listing, only published zones count. When no zone of the table touches the area,
  the published zones unknown to the table (oceanic) are taken.
- **Loading.** A zone is read once, on the first question that needs it; concurrent questions share the same read.
- **Indexes.** Built per zone and per kind on the first question of that kind, in memory, by one-degree cell
  ("floor(lat)|floor(lon)"):
  - points (aerodromes, navaids, points, VRP, obstacles): the cell of the point;
  - airspaces: every cell of their frame; an airspace covering more than 400 cells (FIR, UIR) goes to a "wide" list
    checked on every question;
  - airways: the cells of the segment's frame, up to 64, otherwise the cells of both ends;
  - MORA: one cell per position; identifiers: aerodrome ICAO code, beacon, point and VRP ids.
- **Area questions.** Given `{ bbox: [west, south, east, north] }` or `{ lat, lon, radiusNm }`, visit the cells of the
  area when they are fewer than the index's cells, otherwise the index's cells filtered by the area, so that a whole
  world question is as fast as a large one. Results are exact (filtered by position or frame), without duplicates
  across zones.
- **MORA.** The cell containing the point; `moraFt`, otherwise the "3⁵" notation read back (superscript = hundreds).
- **Identifiers.** Search the loaded zones; when nothing matches, load the published zones one by one until it does.
  `coords` prefers an aerodrome.
- **Place search.** Rank: exact code; aerodrome with an ICAO code whose name starts with the text; town (most
  populated first); other place whose code or name starts with the text; then those containing it.
- **Aircraft types.** Aliases followed to the end (A4M → A400M → A400); the classification rules, the usage names
  (RAFALE → RFAL, H145 → EC45), the display name and the cruise fuel estimate (named type, then ICAO class and wake
  category) are those of the V2 suite. Type search ranks: designator starting with the text, alias or usage name
  starting with it, a word of the model starting with it.

## 5. API

`AeroDB.create({ reader, zones, now })` → service:

| Call | Answer |
|---|---|
| `status()` | `{ published: { zone: cycle } \| null, loaded: { zone: cycle }, missing: [zones], cycle }` |
| `ready(q)` | zones loaded for the area of `q` |
| `on('change', fn)` | `fn({ zone, cycle } \| { changed } \| { aircraft })`; returns the unsubscribe function |
| `airspaces(q)` | airspaces touching the area; `q.types` keeps some types |
| `aerodromes(q)` | aerodromes of the area, or the one of `q.icao` |
| `navaids(q)`, `points(q)`, `vrp(q)` | points of the area |
| `obstacles(q)` | obstacles of the area; `q.minHgt` (ft) |
| `airways(q)` | airways with a segment touching the area |
| `mora(lat, lon)`, `moraCells(q)` | MORA of a point (ft, or null), cells of an area |
| `aar()`, `nat()` | refuelling track files (XML) of the loaded zones, NAT tracks of the day |
| `cities(q)` | towns of the area, or by `q.prefix` (most populated first), `q.n` at most |
| `find(text, n)` | ranked places: `{ label, lat, lon, name, kind, code }` |
| `coords(ident)`, `coordsAll(ident)` | position of an identifier; every place carrying it |
| `aircraft()` | the aircraft base: `canonical`, `related`, `record`, `classify`, `codeOf`, `displayName`, `label`, `perf`, `estimate`, `search`, `size` |
| `stats()` | per loaded zone: cycle, MB read, read time, indexes built |

Every call is asynchronous except the aircraft base's methods once `aircraft()` resolved.

## 6. Invariants

1. aerodb never writes, never builds, never executes a file read from the data repository.
2. A module never names a zone or a file; aerodb chooses them.
3. A question over the whole world returns exactly the published base (same counts as the workstation's base).
4. No interface text: labels, translations and formatting belong to the modules and the frame.
5. ICAO and EUROCONTROL data are never part of the public website.

## 7. Out of scope (later lots)

Splitting each zone by kind and towns by zone (lot 3, publication side, reading both formats meanwhile); the vertical
profile and terrain; airspace activation by date and time; persistence of the indexes between page loads.
