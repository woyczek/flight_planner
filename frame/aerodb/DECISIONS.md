# aerodb — decisions log

The memory of the aerodb agent: every choice, dated, with its reason. No chat history is needed beyond this file,
`SPEC.md`, `INTEGRATION.md` and `docs/technique/V3_SPECIFICATION.md`.

## 21 October 2026 — lot 1 (reading) and lot 2 (API over the published bases)

- **Role taken** by the session that built the SIA publication by zone (V2 lot A, `shared/sia_base.js` `publish`) and
  the aircraft base publication (V2 `/__setup/aircraft-publish`). Worktree `E:\DEFA-v3-aerodb`, local branch
  `v3-aerodb` tracking `origin/v3` (the branch `v3` itself is checked out by the frame's worktree), port 8797.
- **Read side only.** aerodb reads what a workstation publishes and builds nothing: the readers of the source formats
  (AIXM 4.5, XML_SIA, AIXM 5.1, GeoJSON, OpenAir, X-Plane) and the zone split stay in V2 (`shared/sia_base.js`,
  `shared/aero_sources.js`) as long as the launcher builds there. Lot 2 moved the pure data code that the **reading**
  needs: zone frames, cell indexes, place search, the aircraft catalogue (classify, canonical, related, codeOf,
  displayName) and the fuel estimate.
- **Frontier with the frame** (agreed with the frame agent, validated by the ergonomics session):
  - the frame reads and caches files by path: `data.read(path, { policy: 'reference', wait })`, `data.list`,
    `data.watch`;
  - aerodb owns schema, cycle, parsing, indexes and API; it is mounted once as a service and handed to modules as
    `adapter.aerodb`;
  - no module reads `sia/base/` or `AircraftDB/`.
- **Provisional reader** (`AeroDB.fetchReader`): GitHub mode through `GitHubData`; launcher through the served files,
  with no listing. The launcher stays unchanged, as the lot required, and has no directory listing. aerodb therefore
  probes the AIRAC cycle in force and the five before it, zone by zone; the same fallback serves a frame whose
  `data.list` answers `null`.
- **Zone frames instead of contours**: `frame/aerodb/zones.js` (45 KB, 218 zones, one frame per part) generated by
  `tools/build_aerodb_zones.py` from `shared/carto/aero_zones_geo.js` (374 KB). The half-degree margin of V2 is kept.
  A frame is coarser than a contour: a neighbouring zone may be loaded for an area at a border (harmless: a few
  hundred KB).
- **Cycle choice**: the most recent published cycle already in force, otherwise the oldest (published in advance).
- **One-degree cells**, built per zone and per kind on demand.
  - Airspaces over 400 cells (FIR, UIR) go to a "wide" list.
  - Airways are indexed on up to 64 cells of their frame, otherwise on their ends.
  - Large areas visit the index's cells rather than the area's: the first version dropped areas above 40,000 cells,
    and a whole-world question found 5 airspaces instead of 6,753. Fixed, and kept as a check of the bench.
- **Aircraft files**: JSON first (`aircraft_db.json`, `aircraft_perf.json`, the V3 format decided on 21 October), then
  the V2 `.js` read as a JSON literal after `window.NAME =`. Never executed.
- **Fuel estimate table** ported with shortened source notes: same values, aliases and classes as
  `shared/fuel_reference.js`; the class-based source note is in English, since aerodb carries no interface text.
- **Ranking fixes from the bench**:
  - place search ranks exact code, then ICAO aerodromes whose name starts with the text, then towns, then the rest.
    "TOUL" gave hospital helipads first; it now gives LFCL, LFIT, LFBO, LFBF, then Toulouse.
  - type search ranks designators, then aliases and usage names, then model words. "RAF" gave Beech*craf*t types; it
    now gives the Rafale.

## 21 October 2026 — lot 3 (split publication, both formats read)

- **Publication** (`shared/sia_base.js`, V2, `publishSplit`), next to the whole format until the ergonomics session
  ends it:
  - one file per zone, cycle and kind, `sia/base/<zone>/<cycle>/<kind>.json`, all with the same envelope
    (`schema: 2`, `zone`, `cycle`, `kind`, `parserVersion`, `data`, `updated_at`). Kinds: `airspaces`, `aerodromes`,
    `navaids`, `points`, `vrp`, `airways`, `obstacles`, `mora`, `obstaclemax`, `cities`, and `meta` for everything
    else (AAR files, NAT tracks, AIRAC);
  - each town goes to the zone whose contour holds it (then the contour widened by half a degree); towns of no
    published zone are reachable only through `cities_major.json`;
  - `sia/base/cities_major.json`: towns of 100,000 inhabitants or more (6,065 of 70,962, 430 KB). The threshold keeps
    every capital and regional city, so a search for a destination outside the loaded zones still finds it;
  - the manifest `sia/base/index.json`: cycle, ICAO prefixes and file sizes per zone. Zones published by other
    workstations are kept. It lets aerodb know the published zones without a listing (launcher), and go straight to
    the right zone for a code such as `EGLL`;
  - a file is rewritten only when its content (without `updated_at`) changes; older cycle folders of the zone are
    removed. `tools/data_sync.py` needs nothing more: `sia/base` is already in the pool, files and folders alike.
- **Aircraft base as JSON**: the Maintenance button (`/__setup/aircraft-publish`, `tools/launch.py`) writes
  `aircraft_db.json` and `aircraft_perf.json` from the literals of the `.js` files (already checked by
  `tools/data_guard.py`), next to the `.js` files as long as V2 reads them. A second pass finds nothing to do.
- **Reading** (`aerodb.js`): published zones come from the listing, then the manifest, then probing.
  - For the chosen cycle the split format wins.
  - Opening a zone reads `meta.json` only; each kind is read on its first question.
  - Name questions use the loaded zones' towns plus the major towns; area questions use the covering zones' towns.
  - The whole format remains a fallback, with the world's towns. `bench.html?format=whole` checks it.
- **`tools/build_aerodb_zones.py` unchanged**: it reads the zone contours, not the publication.
- **Known limit**: France's manifest lists foreign prefixes (EG for the Channel Islands, LS for Basel-Mulhouse, the
  overseas territories' prefixes). `coords('EGLL')` may then read France's aerodromes (327 KB) before Great Britain's.
  This is harmless and not worth a per-code index.

## 21 October 2026 — mounted by the frame (`FrameData.adapter`)

- `frame/app.js` already mounts aerodb with the frame's adapter. `fetchReader` stays for the bench and for pages
  without the frame.
- **Fix: `watch` reports first arrivals.** The data layer calls `watch` when a reference file first enters its cache.
  aerodb used to forget the zone on every call, so each file it read closed its own zone: `find('TOUL')` lost the
  aerodromes and zones were read again and again. aerodb now keeps the `rev` of every file it read. It forgets a zone
  only when one of those revisions changes, and reads the listing again only for an unknown cycle or zone. Checked by
  republishing `be/…/aerodromes.json`: one `change` event, Belgium read again, the other zones kept.
- **Gap with the local transport, closed the same day**: with the local transport (single user, the default when no
  exchange is ticked), the data layer read no reference file, so aerodb had no data. The frame now takes a read-only
  reference source in that case (the launcher serving the page, otherwise the configured GitHub repository; see
  `frame/DECISIONS.md`). Checked on `frame/index.html` with no usage ticked.

## 22 October 2026 — lot 4 (offline data API, for the Settings screen)

- **`offline` in the service**: `supported`, `zones`, `keep`, `release`, `common`, `aircraft`, all through the reader.
  - Zone names come from the zone table, in four languages.
  - Prefixes and published sizes come from the manifest.
  - States compare the files expected for the zone's chosen cycle with the reader's local copies.
- **Two calls asked of the frame's adapter** (requested through the ergonomics session):
  - `cached(prefix)`: today `read` without `wait` starts a background download, so the state cannot be known without
    downloading everything;
  - `evict(path)`: `remove` would queue a deletion for the repository.
  aerodb detects both calls (`supported()`); until they exist, states are `unknown` and `release` throws. On the real
  adapter today, `keep('fr')` already works (6.9 MB read into the frame's cache).
- **Bench without the frame**: `frame/aerodb/offline_bench.html` uses a bench reader that imitates the frame's
  contract (`read` with `wait`, `list`, `cached`, `evict`) over the provisional reader, with an in-memory cache and a
  network switch. Replaced in lot 4b by the frame's real adapter.
- **Fixes found by the bench**:
  - The manifest was read as `data.zones`, but the publication of lot 3 writes `zones` at the top level. Without a
    listing (launcher), aerodb fell back to probing the AIRAC cycles, and `coords` had no prefixes. Both levels are now
    read.
  - A published zone that could not be read offline was remembered as missing until the next change. It is now asked
    for again at the next question.
  - A kind that could not be read stayed empty, with its index, for the life of the zone. It is now read again next
    time.

## 22 October 2026 — zones chosen by the cells their data cover

- **The problem** (found by maps lot 2): zones were chosen by their frames from the table, widened by half a degree.
  A country's frame overflows it. For a French IFR route (LFRS → LFML, alternate LFMT), Germany, Switzerland and Spain
  were read too: 3.6 MB of Spanish airspaces never drawn.
- **The fix**: the V2 publication (`shared/sia_base.js`, `coverage`) writes in the manifest, per zone, the one-degree
  cells its data cover. The cells come from the points, the MORA cells, the airways sampled every 0.25°, and the
  airspaces' outlines and interiors. They are stored as longitude ranges per latitude row: France 139 ranges, 2.3 KB;
  the whole manifest of the 13 zones 6.8 KB.
  - aerodb chooses a zone when one of its cells is under the area.
  - The frames stay as the fallback when a zone has no cells (old manifest, no manifest).
- **Measured on LFRS → LFML** (the maps module's areas: route area for aerodromes, navaids and MORA, corridor + 12 NM
  for airspaces and airways):

| | Zones read | MB read |
|---|---|---|
| Before (frames + ½°) | de, ch, es, fr | 7.71 |
| After (cells), one corridor rectangle | ch, es, fr | 7.34 |
| After (cells), corridor asked leg by leg | fr (+ es, ch: 96 KB without airspaces) | 3.56 |

  - Spain stays with a single rectangle, and that is right: its data do cover 43° N west of 2° W (San Sebastián,
    Bilbao), and the rectangle around a diagonal route reaches that corner. Leg-by-leg corridor boxes avoid it; the
    maps module uses them from its lot 3.
  - Whole-world questions are unchanged (same counts as the workstation's base).

## 22 October 2026 — towns filed by their country

- **The report**: a town labelled "Béziers" near Châtellerault on a mission map.
- **The cause is not ours**: the label belongs to the base map (OpenFreeMap positron, OpenStreetMap data), in the
  same style as its Poitiers and Châtellerault. With the tiles off, the map shows no town there. GeoNames has Béziers
  at 43.34° N, 3.21° E, and the published towns copy it correctly.
- **The check asked for**: `tools/check_cities.py` (standard library) lists the GeoNames towns outside the contour of
  their country, with the publication's half-degree margin. On the current file: 70,962 towns, 261 outside, 331 of a
  country with no contour.
  - The big ones come from the contours, not from GeoNames:
    - islands missing from Natural Earth 1:50 M (Jeju, Hawaii, Okinawa);
    - disputed areas drawn in another country (Crimea, Western Sahara, Somaliland, northern Cyprus);
    - city states with no contour of their own (Hong Kong, Singapore).
  - Near our zones, it exposed a real fault of the publication, which filed towns by contour:
    - the Zeeland towns (Middelburg, Domburg…) went to Belgium: the simplified Dutch contour misses Walcheren;
    - the Geneva suburbs (Thônex, Plan-les-Ouates…) went to France;
    - Schengen and Vianden (Luxembourg) went to Germany or Belgium.
- **The rule changed, not the entries**:
  - `parseCities` keeps GeoNames' `country` column (`cc`), and the publication files a town under the zone of its
    country whenever that country has a zone, published here or not.
  - The contour stays only for towns of a country without a zone (overseas territories, Gibraltar, Monaco) and for
    towns read before this rule.
  - `cc` is removed from the published files, so their size is unchanged.
  - After republishing: Thônex → Switzerland; the Dutch Middelburg → Netherlands (a Belgian Middelburg exists too);
    Schengen and Vianden → no published zone (Luxembourg is not published); Gibraltar → Spain (no zone of its own).
- **Seen in the source**: the GeoNames extract (`shared/carto/villes_geonames.csv`) holds only 2 towns for Portugal
  and 43 for Ireland. A fuller extract is a data task, not a rule.
- **Develop does not have the split publication**: `publishSplit`, `coverage` and this rule exist only on v3.
  `parseCities` is shared, but the rest belongs to the port of lot 3 to develop when the ergonomics session decides it.

## 23 October 2026 — lot 5a, the aircraft registry

- **The user's decision**: all aircraft data in aerodb, in one place, fed from every source. The `.lnmperf` files
  become an output kept in sync (lot 5b). Answers of the ergonomics session to the reading:
  - one file per sheet;
  - mission aircraft through the reference and the fleet only;
  - the lnmperf folder set in the V3 Settings of a launcher page.
- **One file per sheet** (`aircraft/sheets/<id>.json`): small merges, a git history per sheet, one to one with the
  `.lnmperf` files.
  - V2's `fpdb.json` is adopted in reading, never rewritten in bulk; a sheet is written at its first change.
  - Until V2 is switched off, aerodb mirrors each sheet into the `fpdb.json`, with `updated_at` and `updatedAt` both.
- **Field-level origin** (`_fields`, `_kept`) in the sheet itself: the frame's merge function for `aircraft/sheets/`
  sees both versions' stamps, so a phone and a workstation editing different fields both keep their change.
- **`sheets.js` taken over** as `frame/aerodb/sheets.js` (`AeroDBSheets`). Changes:
  - aerodb configures it with the fleet; fuel never passed it, so the fleet line of the ChatGPT prompt was empty;

  - a latent bug of fuel's copy is fixed: `KG_PER_LB` was used twice but never defined, so a ChatGPT reply or a sheet

- **Search kept separate from the types' search**: `search` is now the registry's (asynchronous); the catalogue's type

  - `watch(PUB)` also reads the list again when the previous listing found nothing;
  - `watch('AircraftDB/')` also reacts to a file never read, for instance a base pushed after the app was opened;
  - the registry's watchers ignore the arrivals of its own first reads.
- **Frame files touched**, with the frame session told:
  - `frame/app.js` mounts aerodb with `AeroDB.declaration()`;
  - `frame/sw.js` keeps `aerodb/registry.js` and `aerodb/sheets.js`.
- **Tests**: `frame/aerodb/test/registry.html`, 21 checks on the real data layer (local transport, references from
